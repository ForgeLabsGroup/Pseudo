# Render deployment

Deploy `apps/web` and `apps/api` as two Node web services from the repository's `main` branch. Keep the root directory blank: both apps import workspace packages. Supabase continues to provide Postgres, Auth, and Storage.

`render.yaml` describes both services. The current services were created directly with the Render CLI and already track `main`; merging this file does not attach them to a Blueprint. For a new deployment, create a Blueprint from this repository and select `main` after the configuration is merged, or create services with the CLI. Avoid creating a second pair of services if they already exist.

Both services run in Virginia. The API uses Starter compute to keep scheduled publishing running; the frontend uses free compute and sleeps when idle. Render may require payment information before allowing service creation, even for free compute. Generation jobs run inside the API and can be interrupted by a restart or deploy.

Current deployment:

- Frontend: https://pseudo-web.onrender.com
- API: https://pseudo-api-tmoh.onrender.com (health check: `/health`)
- Both services enable automatic deployment from `main`.

## Environment

Set `SUPABASE_URL`, `SUPABASE_ANON_KEY`, and `SUPABASE_SERVICE_ROLE_KEY` on the API. Copy the selected provider settings and credentials from the local environment to the API only. Set `CORS_ORIGINS` to the actual frontend origin, without a trailing slash. For token encryption, use a stable key generated by `openssl rand -base64 32`.

The frontend receives only `NEXT_PUBLIC_SUPABASE_URL`, `NEXT_PUBLIC_SUPABASE_ANON_KEY`, and `NEXT_PUBLIC_API_URL`. Use the API's actual public HTTPS URL. These variables must be present during the Next.js build; changing them requires rebuilding the frontend.

The build installs development dependencies explicitly because the Next.js build needs TypeScript and Tailwind tooling. The API runs TypeScript through its `tsx` dependency and installs the standalone yt-dlp binary during its build. ffmpeg is provided by `ffmpeg-static`.

## Database and login

All API routes except the GET/HEAD health check and CORS preflight require a Supabase access token verified against this project's Auth service. All current and future Supabase users may access the API; there is no email or user allowlist. Invalid, expired, or missing sessions are rejected before route handlers run. Anyone who can sign up or sign in with shared demo credentials receives this same access.

The API permits ten write requests per signed-in user per minute, returning `429` and `Retry-After` after that. This limit is held in memory per API instance and resets on restart; it is not a dollar budget or a distributed quota. Use provider spending limits for a financial cap. Query-string tokens are accepted only on GET `/api/events`; application request logs omit query strings. Other routes require a bearer Authorization header.

These controls take effect only after this code is deployed. Merging into `dev` alone does not update the services that track `main`.

Apply pending migrations to the intended Supabase project before using the deployed app. Do not seed production demo accounts automatically. Set the Supabase Auth Site URL and any required redirect URLs to the frontend's production URL.

## Verify

Confirm the API's `/health` returns `{"ok":true}`, open the frontend login page, and verify authenticated API requests succeed with the configured CORS origin. Check deployment logs for both services. Auto-deploys track commits to `main`.
